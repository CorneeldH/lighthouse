    Skills

    A skill is a set of instructions the model follows. A workflow skill you or another skill start; a standard skill the model picks up by itself when its description matches the task.

    Agents

    An agent is a subagent with its own context, started for one narrow job.

    Hooks

    A hook is a script the harness runs on an event, such as a tool call, and it can check, format or block.

    GitHub

    lighthouse keeps the work on GitHub, not in files in the repository: what to do lives in issues and milestones, what was done in pull requests. The skills read and write them with gh; [forge] in lighthouse.toml names the repository. Most of it is a way of working the skills carry, not a file init installs.

    Issues

    One issue is one piece of work. /lighthouse-write-issue writes it from one of two forms: a bug (broken behaviour you can reproduce) or a task (everything else), each with its acceptance criteria and its Definition of Done. The forms live in the skill, not in .github/ISSUE_TEMPLATE/, so a session writes the same issue as a person filling in a form would. Before it writes one, the skill searches for an issue that already covers the work. The acceptance criteria are what /lighthouse-write-pr proves and /lighthouse-close-issue checks again after the merge.

    Milestones

    A milestone is a larger block of work, at least about five issues. Its description is the pitch: the problem, the appetite, the solution, the rabbit holes, a Definition of Done and the no-gos. A milestone without a Definition of Done does not exist. The description is also the gatekeeper: an issue goes into a milestone only when it brings that Definition of Done closer, and otherwise to the backlog, with no milestone.

    Labels

    A blocking label says what stands in the way of the next step: the work is not shaped yet, waits on a decision, on another issue, on a third party, on hands or on a test by a person. At most one at a time; an issue without one is ready to pick up. A block on another issue is first a blocked_by relation on GitHub, then the label. [labels] in lighthouse.toml names the labels; init does not create them on GitHub.

    The board

    Optional: a GitHub Projects board, configured in [forge.board]. Labels and milestones say what an issue is; the board adds only its status (To do, In progress, Done, On hold) and a priority. /lighthouse-start-issue moves an issue to In progress. Without [forge.board] the skills skip it.

    Pull requests

    Every change goes through a pull request and is squash-merged. /lighthouse-write-pr writes the body: Closes #N with an evidence table, one row per acceptance criterion, or Refs #N or No issue with a reason. The hook pr-create-gate blocks a gh pr create without one of those.

    What init puts in .github/

    Two files, and no more. The pull request template becomes .github/pull_request_template.md. The GitHub Actions workflow unblock-dependents becomes .github/workflows/lighthouse-unblock-dependents.yml: when an issue closes as completed, it removes the blocking label from every issue that waited only on it. It acts as a GitHub App, so init installs it only when [ci] names that app's keys. init installs no CI, no release workflow and no issue templates: those stay your project's own. The ones in this repository's .github/ are lighthouse's own.
